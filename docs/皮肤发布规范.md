# 皮肤开发与发布规范

规范版本：1。开发从 [skin-dev](https://audcore.utae.cn/skin-dev/) 开始，接入方法见 [皮肤开发指引](皮肤开发指引.md)。当前提供可执行的 `web-static`，以及三款原生示例使用的 `msvc-script`。其他编译器、CMake、Rust 和编译型网页须先人工接入对应 recipe，不会仅凭声明自动执行。

## 仓库与元数据

每个仓库对应一个皮肤，根目录提供 `manifest.json`、`README.md` 和明确许可证。首次通过 `skins.md` 的一行 PR 登记 ID、名称、类型和仓库，人工审核来源、许可、能力及构建规则。官方再分发所需的代码、资源许可必须完整。

`manifest.json` 是元数据唯一来源。保留现有运行字段 `id`、`name`、`names`、`version`、`api`、`entry`、`preview`、`window`、`themes`、`scale`、`languages`，新增 `kind`、`license`、`repository`、`description`、`descriptions` 和 `build`。`kind` 使用 `web` 或 `native`，不以文件扩展名猜类型。当前网页运行契约要求三段数字版本。

`names` 和 `descriptions` 使用 `zh`、`en`、`ja` 语言键；默认 `name` 和 `description` 为缺少对应翻译时的回退。`languages` 表示皮肤界面实际支持的语言，与介绍翻译分开。README 用于介绍、截图、使用及开发说明，不嵌入机器配置。官网读取获准提交的内容，限制 Markdown 渲染，不执行作者 HTML 或脚本。

## 静态网页构建规则

```json
{
  "build": {
    "schema": 1,
    "recipe": "web-static",
    "platform": "windows-x86_64",
    "toolchain": {
      "tools": { "node": "24.12.0" }
    },
    "files": [
      "web/index.html",
      "web/main.mjs",
      "web/style.css",
      "web/preview.png"
    ]
  }
}
```

此 recipe 无需编译器。Node.js 是打包工具，必须填写实际精确版本；官方匹配并核对版本，不自动升级或下载作者指定的任意工具。

所有路径相对仓库根目录，文件清单不能包含 `manifest.json`，运行清单由官方工具生成并剔除 `build`。禁止路径越界、符号链接和目录联接；包格式校验进一步检查大小、重复路径、接口与入口配置。静态 HTML、CSS 和 JS 的字面量资源引用必须位于包内。此引用检查不是完整安全审查，动态构造的 URL、调用行为和宿主桥接能力仍须审查。

官方使用自己受控的构建器，而不是执行候选仓库里的工具副本。表格仓库附带的 `tools/` 用于独立构建和开发参考，官方版本更新后可按审核记录固定工具版本。

```sh
node tools/build-package.mjs <固定提交的源码目录> <输出目录>
```

打包器不执行项目脚本，按固定顺序生成 ZIP，去除环境时间影响；文件名为 `ID-v版本.skin.audcore`。同一源码与相同工具链应产生相同字节，已有输出仅在内容一致时复用。

## 需要编译的项目

编译 recipe 使用 `build.toolchain.compiler`（编译器名称、精确版本）、`sdk`（名称、精确版本）和 `tools`（构建工具版本）。MSVC 填实际编译器版本，不只填写 Visual Studio 年份。Rust 项目还须固定目标工具链，Node 项目固定包管理器；依赖、子模块及外部下载都必须有固定版本和锁文件或校验值。

编译步骤使用命令和参数数组；即使不用 shell 拼接，构建脚本和依赖仍属于不可信代码。原生 `output` 指向实际 DLL，网页 `output` 指向生成的资源目录。官方负责校验、最终打包及命名。web-static 不执行编译步骤；现有原生示例通过独立 msvc-script 实现，接入其他 recipe 须人工审核并实现。

## 审核与发布边界

1. 首次登记和首次产物人工审核，固定候选 tag 对应的完整 commit。
2. 以最后批准的 commit 为基准审查到候选的全部变化，不能只检查最后一次提交。
3. 在无发布凭据、无宿主敏感目录的隔离环境构建；构建结果不得直接取得签名权限。
4. 校验资源、版本与身份，完成真实宿主的必要功能验收；通过后才将精确产物交给独立发布阶段。
5. 记录源码 commit、构建器版本、实际工具链、产物大小与 SHA-256；生成签名目录。版本必须与候选 tag 一致，不覆盖同版本的其他内容。

普通网页皮肤更新可以在规则满足时采用自动检查与 AI 辅助审核。新增依赖、构建规则、联网行为、二进制、维护者或仓库变更、许可变化及不确定结论均转人工。原生代码更新初期每版人工批准；原生皮肤在宿主进程内执行，AI 审核及签名不构成沙箱或安全保证。

作者内容全部是被审材料，不能作为审核器执行指令。AI 不持有发布密钥，其结论由固定策略处理。

官方将项目状态、候选审核状态、已发布版本分别维护；候选失败不影响旧版继续提供。暂停接收更新与撤下危险产物是不同操作。作者不能通过更改 manifest 自行设置审核结果。

## 当前落地范围

已提供项目登记表、各皮肤独立源码、静态网页打包器及三款原生构建示例。成品皮肤以独立仓库为唯一来源，主仓库保留公共接口、通用控制器、开发与测试夹具和内置默认兜底界面。每日发现任务、AI 服务接入、官网第三方列表渲染及自动签名发布尚未启用；现有官方目录继续沿用原发布流程。

## 登记表格式与初次 PR

在根目录 `skins.md` 按行维护以下四列，项目仓库初期使用 GitHub：

```markdown
| ID | 名称 | 类型 | 仓库 |
| --- | --- | --- | --- |
| org.example.skin | 示例皮肤 | web | https://github.com/example/skin |
```

ID 与包一致，收录后保持稳定；派生为另一个项目时使用新 ID。名称方便人工阅读，国际化名称以作者清单为准。类型只用 `web` 或 `native`，由产物核实。表中不重复维护版本、简介、图片、语言及审核状态。

初次 PR 人工核对来源、维护者、许可、能力、构建和实际效果。登记合入代表进入收录流程，首次产物审核发布后才进入可下载列表。作者仓库固定读取根目录 manifest.json 和 README.md。

## 作者文件分工与主页入口

```text
manifest.json       # 元数据、运行要求和构建方法的唯一来源
README.md           # 介绍、图片、安装、开发和反馈说明
LICENSE             # 自有代码许可，另保留第三方许可
web/ 或 src/        # 源码与资源，目录可按项目组织
tools/              # 可选的开发工具与打包器副本
```

不要求额外 AUDCORE.md，不在 README 的 YAML 文件头、HTML 注释或自然语言中解析机器配置，因此不影响 Markdown 的正常展示。README 写明实际版本、类型、语言和主题、宿主接口要求、安装方法、构建命令、输出位置、已知限制、许可证及第三方来源。封面示意和实际截图应明确区分。

每款主页必须同时提供：

- [声核官网](https://audcore.utae.cn/)、[下载声核](https://audcore.utae.cn/download/)、[使用指北](https://audcore.utae.cn/guide/)
- [skin-dev 皮肤开发入口与 SDK](https://audcore.utae.cn/skin-dev/)
- [本规范](https://github.com/audcore/audcore-document/blob/main/docs/皮肤发布规范.md)、[项目登记表](https://github.com/audcore/audcore-document/blob/main/skins.md)
- 皮肤自身 Issues，以及 [声核本体问题反馈](https://github.com/audcore/audcore-document/issues)

## 网页 manifest 完整基础示例

```json
{
  "id": "org.example.skin",
  "name": "示例皮肤",
  "names": { "zh": "示例皮肤", "en": "Example", "ja": "例" },
  "description": "以表格呈现通道和路由",
  "descriptions": { "en": "A spreadsheet-style mixer skin." },
  "author": "example",
  "version": "0.1.0",
  "kind": "web",
  "license": "MIT",
  "repository": "https://github.com/example/skin",
  "api": { "major": 1, "minor": 0 },
  "entry": "web/index.html",
  "preview": "assets/preview.png",
  "window": {
    "default": [960, 640],
    "min": [480, 320],
    "max": null,
    "resizable": true,
    "maximizable": true
  },
  "languages": ["zh", "en", "ja"],
  "themes": ["dark", "light"],
  "scale": { "min": 0.75, "max": 2, "default": 1 },
  "build": {
    "schema": 1,
    "recipe": "web-static",
    "platform": "windows-x86_64",
    "toolchain": { "tools": { "node": "24.12.0" } },
    "files": ["web/index.html", "web/main.mjs", "web/style.css", "assets/preview.png", "LICENSE"]
  }
}
```

`names` 与 `descriptions` 使用 zh/en/ja 翻译，缺失时回退默认 name/description。`languages` 表示界面实际语言，与介绍翻译分开。网页接口为 API 1.0，原生示例为 ABI 0.2，不能混用。窗口尺寸使用逻辑客户区，最大尺寸可为 null。入口只能是包内 HTML，不能指向系统程序。在线封面按现有发布流程提供 4:3 PNG。

源码可以公开开发，但不会直接追踪 main 进入官方列表。官网从获准的同一提交读取 manifest 和 README，不能实时抓取审核后的任意修改。

## 原生工具链与输出示例

```json
{
  "build": {
    "schema": 1,
    "recipe": "msvc-script",
    "platform": "windows-x86_64",
    "toolchain": {
      "compiler": { "name": "msvc", "version": "19.44.35222" },
      "sdk": { "name": "windows-sdk", "version": "10.0.26100.0" },
      "tools": { "msvc": "14.44.35207", "python": "3.14.2" }
    },
    "steps": [["powershell.exe", "-NoProfile", "-File", "build.ps1"]],
    "output": "build/skin.dll"
  }
}
```

compiler.version 是 cl.exe 的实际版本；tools.msvc 是 VC Tools 安装目录版本，不能只写 Visual Studio 年份。实际使用的 CMake、Ninja、Rust、Node 和包管理器同样填写精确版本；Rust 还需目标工具链，必要时补 MSVC 与 SDK。没有匹配环境时转人工，不自动替换成最新版。工具声明与实际验证是两回事，具体核对范围以构建器和发布记录为准。

| 规则 | 输入 | output 与最终交付 |
| --- | --- | --- |
| web-static | 显式 files 清单，无编译器 | 不需要 output，直接生成运行清单与 ZIP 格式皮肤 |
| 编译型网页（待接入） | 固定工具链、steps | output 为网页资源目录，例如 dist，之后统一打包 |
| msvc-script 原生示例 | 固定工具链、steps | output 为真实 DLL，例如 build/skin.dll |

steps 使用命令与参数数组；脚本仍是隔离环境中的不可信代码。路径相对仓库，禁止越界。原生仓库也提供统一 manifest，但运行身份和 ABI 仍来自 DLL，构建后核对清单、导出信息与版本资源，不能只改 JSON。示例仓库提供本地包装步骤，官方发布从精确构建结果独立核验后再签名。

最终交付统一为 `ID-v实际版本.skin.audcore`；网页内容是 ZIP，原生内容是 DLL。构建中间文件不作为另一个下载版本。运行清单剔除 build，files 不手填 manifest.json，并包含必要许可证。所有代码、资源、SDK 和构建依赖均不得隐式读取声核私有仓库或作者相邻目录。

## 无变化时跳过

以后只从对应独立仓库更新，不在本体保留副本。比较真实构建输入及受控构建器版本，不仅比较分支名或最后一次提交。未参与打包的 README 等文档变更不触发编译；参与包内容的资源或许可证变化仍属于输入变化。

只有上次构建成功且最终产物大小、哈希校验通过的记录才能作为跳过依据。输入未变但产物缺失或损坏时不能跳过；构建失败不更新成功记录。源码、构建规则或产物变化仍遵守版本不可覆盖和人工/AI 审核规则，跳过构建不等于批准新的介绍或绕过发布审核。

## 项目名称与说明排版

仓库名直接说明界面形式或操作用途，例如表格调音、节点连线、电平仪表盘。About 使用简短中文说明用途，README 开头写实际布局和常用操作，不以抽象原型名或“独立皮肤与开发参考”代替介绍。

同一皮肤的后续版本优先在原仓库升级，不为版本号重复建立维护项目；不同布局的独立皮肤应通过名称说明区别。仓库改名保持皮肤 ID 稳定，README 写明安装列表中的实际名称，避免误改工程身份。

参考来源、移植文件、许可证、美术资源及验证状态分别写成短段落或列表。长命令分行，链接标签保持简短；不把所有说明挤成一个长段落。
